1. 背景与目标

本体痛点：当前胜利只有一条路——堆到 winVp(默认 15) 声望。后段易陷入「各刷各的、谁先到 15 谁赢」的漫长拖局，缺乏冲刺感与路线博弈。

借鉴来源：Splendor《城巿》在开局翻开若干「城巿牌」，玩家在回合结束时若满足某城巿条件，可立即获胜，无需先到 15 prestige。

主题映射：城巿 → 神谕碑。众神降下神谕，凡人竞相完成以获神恩（即时胜）。

关键结构决策（v0.2）：神谕是独立游戏模式（开局可选），不是叠加在所有模式上的常驻层。这样「神谕模式」与「经典模式」「无神模式」互不污染，玩家按需选择。

2. 核心机制

2.1 生命周期

  • 开局：仅当 oracleMode 开启时，按 playerCount + 1 翻开神谕碑（3 人局 4 张），公开陈列于「神谕区」。
  • 条件：每张碑 = 一个胜利条件（见 §3）。全部基于公开可验证状态。
  • 判定时机：在 finishTurn 的回合真正结束前（声望终局判定之后、移交回合之前）统一校验当前行动者。
  • 触发：满足任意一张未认领的碑 → 立即 phase="over"、winner=[pIdx]，发 oracle 事件（覆盖 winVp）。
  • 认领：触发后该碑标记 claimedBy，从可触发池移除。

2.2 回合结束结算顺序

→
贵族结算eligibleNobles → 接待
→
声望终局winVp / endTrigger
→
神谕校验checkOracles(pIdx)
→
移交 / 胜利

4. 与现有系统的接口

4.1 数据模型

st.oracleMode = true;                 // newGame 选项开启
st.oracles = [                        // 仅 oracleMode 时由 initOracles 填充
  { id: "oracle_0", type: "color",   claimedBy: null },
  { id: "oracle_1", type: "nobles",  claimedBy: null },
  // …
];

4.2 新增函数（已落地，导出可用）

  • initOracles(st) — 抽 playerCount+1 个互不重复类型。
  • oracleSatisfied(st, pIdx, type) — 纯函数判断。
  • checkOracles(st, pIdx) — 遍历未认领碑，命中即置 winner 并返回该碑。
  • oracleProgress(st, pIdx, oracle) — 返回 {name, desc, parts:[{label,cur,target}]}，供 UI 在声望位渲染每人进度。

4.3 UI 接口要求（P2，待实现）

  • 独立模式入口：开局设置页增加「神谕模式」开关，与经典/无神并列、互不冲突。
  • 神谕区醒目：右上（类比贵族区）常驻显示神谕碑，带持续动态效果（如脉冲光晕/流光），强调其为额外胜利路径。
  • 每人进度在声望位：每个玩家面板原声望显示处叠加其神谕进度（如「红 4/4 ✓ 蓝 4/4 ✓」），让玩家一眼看到离神谕还差多少。
  • 神谕胜利演出：收到 oracle 事件时播放专属演出。

5. 配置与平衡

  • 碑数量：默认 playerCount + 1（3 人局 4 张）。
  • 主路关系：winVp 仍是主胜利条件；神谕是并行捷径。
  • 观测（v0.2 实测）：120 局神谕模式 AI 互打（AI 尚不主动追神谕），神谕胜 50 / 声望胜 70，0 崩溃。说明条件在「无意积累」下约 42% 触发——人类主动经营时会更可控；若觉过频，调高条件门槛即可（仅改 ORACLE_TYPES 阈值）。

6. 实现阶段

  1. P0turn-end 守卫：神谕校验接入 finishTurn 声望判定之后，且仅在 st.oracles 非空时执行——非神谕模式零副作用。
  2. P1纯逻辑 + 单测：initOracles/oracleSatisfied/checkOracles/oracleProgress 全部落地，oracle_test.js 76 断言全过（满足即赢 / 差一步不触发 / 进度结构 / 非神谕零回归 / 120 局不崩）。
  3. P2界面（待实现）：独立模式开关 + 醒目动态神谕区 + 每人进度在声望位 + 神谕胜利演出。
  4. P3AI 接入：aiChoose 把「距某神谕还差几步」纳入评分（复用 focusColors/目标聚焦思路），让 AI 也会抢神谕，而非纯靠无意积累。
  5. P4回归与发布：sim_audit 1950 局 0 非法/0 崩溃 + 神谕触发率监控 + 重新发布。

7. 风险与开放问题

  • 触发频率：当前实测约 42%（AI 不主动追）。若过频，调高 ORACLE_TYPES 阈值即可，无需动结构。
  • 与酒神赐福/永久折扣交互：checkOracles 位于 finishTurn 末尾，所有 phase 收尾后，宝石/卡已计入，无时序问题。
  • 多人同回合满足：取最先匹配者（即时胜语义），无优先级问题。
  • UI 动效成本：持续动态效果需控制性能，避免每帧重排；建议 CSS 动画 + 轻量 DOM。

8. 验收标准

  • 单元：满足各类型即 phase="over" 且 winner=[pIdx]；不满足绝不误触发（已覆盖）。
  • 回归：非神谕模式整局照常；神谕模式 120 局 0 崩溃（已验证）。
  • UI（P2 待补）：模式开关生效、神谕区常驻动态、每人进度在声望位正确渲染、神谕胜利演出正常。
  • 发布：线上链接实测若干局无异常。
